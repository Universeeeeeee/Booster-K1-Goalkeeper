# H0：G 预测器与控制调用 wall-clock 审计

当前同步 G 刷新不能据此声明为 50 Hz 实时控制。三类保存状态的完整刷新都超过 20 ms 策略预算；长滚动的全部 20 次刷新超过 100 ms，弹跳有 1 次超过 100 ms。预测运行时调用方仿真时间没有推进，但实际 wall clock 已流逝，调用线程被阻塞。

可复现命令：

```sh
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python scripts/benchmark_defense_prediction.py
```

机器可读结果：[predictor_latency.json](../reports/defense_validation/predictor_latency.json)。该文件包含每次原始耗时、median/p95/max、预算超限次数、运行环境、代码与保存数据 SHA-256、完整保留文件清单。

## 测量范围

在 macOS 26.4 arm64、Python 3.13.13、MuJoCo 3.3.7、NumPy 2.3.3、Torch 2.9.0 CPU 单线程上，每项预热 3 次后计时 20 次。使用 `perf_counter_ns`，p95 由 NumPy 线性插值计算；这些有限采样统计不是最坏时延上界。

固定选择 G 原有 `reachable_left_g_active`（长滚动）、`bouncing_g_active`（弹跳）、`air_center_g_active`（空中）轨迹中首个不早于 2.02 s 的完整当前 qpos/qvel 状态。选择规则不依赖防守结果。三份 trajectory 内部哈希均匹配原 summary。预测模拟的未来时长分别为 9.716、4.845、0.869 s，覆盖四个原 G 请求平面；完整刷新包含原三次 current/target/decision coverage 查询，机器人碰撞 geom 共 20 个。

只创建独立 MuJoCo data；不生成新的防守轨迹，不实现或运行新手臂动作。官方源代码与权重通过已有 manifest 校验。官方控制另测已有 gait `compute_targets` 和 `step`，后者包含原 PD 更新及 20 个 1 ms 物理子步。官方 history 在相同当前状态上预热，原轨迹未保存完整策略 history，所以这不是原完整历史的动作重放，也不用于重新判定 A–G 防守结果。

计时排除模型构造、状态恢复、控制器构造和磁盘 I/O；正式 `command` 计时保留父类观察、原 F 基线预测、G 预测、coverage、决策、记录与缓存更新。独立 predictor 与 coverage 测量作为成本参考；不同串行采样段存在机器负载和缓存变化，不能把它们的统计分位数相加当作完整 command 分位数。

## wall clock 与仿真时间

每个预测、coverage、完整刷新、非刷新和官方纯推理计时调用前后，直接读取调用方 `MjData.time`，测得差值严格为 0；G 调用还检查调用方 qpos、qvel、ctrl 保持一致。官方完整 `step` 在独立克隆里前进约 0.020 s，容差 1 ns。

G `BallPredictor` 在自己的 `MjData` 上做逐步未来模拟，原调用方数据不前进。高层循环同步等待 `command` 返回，因此仿真轨迹在预测期间没有时间跳跃，现实中的墙钟、传感器观测年龄和电机控制截止时间却继续前进。离线轨迹的确定性无法证明硬件 50 Hz 控制时序成立。

## 当前可用的 runtime 限制

原 G 已有 18 s horizon / 18,000 个 1 ms 预测步的数量上限，以及按**仿真时间**判断的 100 ms 刷新间隔。原实现没有 wall-clock deadline、取消机制、后台预测或异步控制交付；18,000 步上限不能换算成有保证的实际耗时上限。

100 ms 刷新间隔不提供 20 ms 控制截止时间以外的同步运行额度。当前证据支持将该实现用于离线仿真审计；需要实际 50 Hz 控制时，应先解决预测工作与控制截止时间的隔离、过期结果处理和完整运行链路时序验证。本次只审计，没有改动 G 调度或预测行为。

本次仅覆盖三个早期当前状态、单台机器和有限重复数；未覆盖所有后期状态、完整无交叉 horizon、首次冷启动、传感器、网络、viewer 和操作系统调度抖动。没有实时能力声明。

运行前后比对 724 份原有报告、相关源码和测试文件哈希，全部一致；原 A–G 数据、官方实现、G 源码及原测试均未改动。

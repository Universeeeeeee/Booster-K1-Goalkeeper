## 依据与暂定成像模型

来源为根目录 T3定制相机需求说明书 中的 Markdown 需求及 Sentinel_T3_产品规格书20261030.pdf（V0.2）。PDF 第 1 页单列 RGB 全局快门、114°×98° FOV、1600×1200 @30fps（可配置低分辨率）。100fps 以上模式没有硬件承诺或模式表，是用户本阶段的仿真目标。像素总量减少不能单独证明传感器读出、接口和 ISP 可以同比加速。

这是候选参数，非实测标定；畸变暂不建模，曝光暂为瞬时全局成像。规格书 114°×98° 的 FOV 不用于覆盖用户指定 K；候选 K、规格书 FOV 与真实畸变模型的关系留待实机标定。早期基于 FOV 的调试运行只用于排查出图，不属于最终 ROI 验收。

## 帧率瓶颈与后续优化评估

园区对照：2 线程优于 8 线程（500 帧短测含 fsync 52.80 vs 50.15 fps）；Fabric 场景委托仅小幅变化（53.46 fps）。短测会被最后约一秒的同步开销显著拉低，不据此推断持续上限。60Hz 的 7200 帧首次长测平均 61.136 fps，但 5s 窗口最低 59 fps，因此记录为失败，未放宽阈值。

最终通过版本分段平均耗时：场景/编号更新 0.871ms，World.step/render 12.616ms，GPU→CPU 取图 1.682ms，RGB 整理 0.399ms。中位数分别为 0.758、12.284、2.008、0.392ms；分布不同，不能混用平均数和中位数相加。完整分布见本地 bottleneck.json。World.step 包含 CPU 场景同步、渲染调度、GPU 等待等，不是独立 GPU kernel 时间；没有 GPU trace 前不能简单将其全部归为 GPU 算力不足。运行中 GPU 利用率样本约 19%–31%，也不支持“显存或 GPU 算力已经满载”的结论。

抗锯齿请求 0 曾被当前渲染模式自动改回 DLSS（3），不能把设置成功视为已生效。最终增加 limitedOps=false 并在 render product 显式设置 none，读回为 0。DLSS 是时域重建，不是本轮使用的帧生成；本轮从未用帧生成、插帧或重复图像提高帧数。

后续恢复 100fps 开发时建议按以下顺序推进：

1. 使用 Kit CPU profiler 和 GPU trace 拆分约 12ms 的渲染调用：USD/Fabric 同步、场景更新、渲染提交、GPU kernel、同步等待分别测量。相机随清洁车移动时的整车层级更新应重点检查。保持场景资产与交通状态一致做 A/B。
2. 把 GPU RGBA→RGB 与 pinned-memory 异步拷贝组成双缓冲流水线，减少约 1.7–2ms CPU 等待；需要再次验证像素编号与源位姿，不能直接挪时间戳掩盖流水线延迟。
3. 诊断条目前每帧修改若干 USD visibility，可改成单次 GPU 编号写入，但必须保留独立的场景时间/位姿证据。当前在线编号验证约束是数据正确性的基础，不应直接删除再报告更高帧率。
4. 以同场景、同 ROI 做渲染质量对照（反射、间接光、采样等），先量化图像差异再决定是否采用。当前未为了吞吐删建筑、行人、材质或缩小 ROI。降分辨率属于改变目标规格，应另列档位。
5. 压缩录制可降低磁盘带宽与文件体积，但增加编码负载且可能有损；100fps RGB8 约 144MB/s，60fps 约 86.4MB/s。有界异步写盘已把主要写入成本移出渲染关键路径，单纯更换 MP4 不足以解决约 12ms 渲染调用。

从约 64fps 到 100fps，需要总帧时间从约 15.6ms 降至 10ms，缩短约 36%。即使完全消除约 2ms 取图/整理成本，约 12ms 渲染调用仍超出预算，所以优先优化场景同步与渲染，而非只改编码器或增加线程。200–250fps 预算仅 5–4ms，当前证据不足以承诺同画质、同园区场景可达。

## 密集颗粒修复
